# 产品原型智能演示设计方法论（AI Studio 适配版）

一句话总纲：**好的演示不是模拟用户点击页面，而是重放一个业务事件驱动的状态机——用可回放的状态快照，让用户看到系统"为什么"这样变化。**

（源头方法论沉淀自 Agent 工作负载页 / AI Coding 平台 / 文档版本 Diff / 图谱变更等 Demo；本文件是其面向 KiroCrew AI Studio 文档工作台的适配与落地规范。落地实现见
[`website/src/apps/ai-studio/demo/`](../../website/src/apps/ai-studio/demo/scenario.md)。）

## 一、演示的目标是"业务闭环"，不是页面跳转

每一段演示必须回答四问：为什么发生变化？谁触发的？系统内部发生了什么？结果是什么？

AI Studio 的标准闭环（本应用的主业务链，演示必须演它）：

```
用户编辑 requirements.md
  → 首次变更立即自动保存落一条草稿记录（diff 亮必有记录，无空窗）；后续输入停手 2s 再落
  → diff 图标由灰变亮（有未提交修改）
  → 用户点 diff，看到 红删绿增
  → 用户点提交
  → 旧内容进版本快照(vN)、修改历史清空、diff 图标回灰
  → 提交喂需求图谱：新需求进图（图谱节点/边 +Δ，演示高亮本次新增）
  → 用户点发版：AI 按图谱生成代码（过程感：解析图谱 → 文件清单 → 完成）；
    每个生成文件标注源自图谱哪个节点——需求→图谱→代码的追溯链合龙
  → 发版后 AI 把冻结文档"沉淀"为结构化设计事实：候选变化(新增/修改/移除，
    各注明来源段落)→ 采纳 → 图谱吸收并高亮本轮波动——需求→图谱→代码→再沉淀
    的因果链完整（图谱不是提交直接出的，是发版后沉淀出来的）
  → 结构化事实反向重生成文档：新版本出现并标注来自哪次沉淀；三段成组 Diff
    （用户改动/结构化变化/重生成差异）按业务点联动——用户核对"系统理解了
    对不对"（反向链路：结构化数据 → 文档）
  → 基于冻结设计开始开发：开发记录锚定"重生成版本 · graph@沉淀"（追溯起点），
    四阶段（任务生成→编码实现→测试验证→构建打包）推进靠快照帧不靠计时器；
    全部完成才出产物三件套与可运行版本
  → 打开可运行版本：仅在演示 overlay 内部切到内置快照组件（无服务器/容器），
    体验页功能清单逐字等于图谱需求节点——"可运行"正是结构化设计承诺的
```

反例（禁止）："点图标 → 弹层出现 → 关闭"——这是 UI 动画，不是业务。

## 二、先设计状态机，再写演示脚本

对象与状态：

- **文档**：`干净` → `草稿(有未提交修改, 含 N 条自动保存记录；N≥1——首次变更立即落记录)` → `已提交(vN)`
- **diff 图标**：`灰`（当前内容==最近提交）/ `亮`
- **修改历史图标**：`灰`（上次提交以来 0 条）/ `有 N 条`（提交后清零）
- **版本历史**：`v1..vN`，每版携带"vs 上一版"的 diff；v1 无前驱，整篇按新增
- **需求图谱**（携带它的世界才有）：节点=需求/文档/模块，边=追溯/依赖；提交使图谱 +Δ，快照携带 `graphDelta`，且必须等于前后快照的集合差（生成器交叉校验）
- **发版与生成代码**（携带它的世界才有）：`已发版(版本)`，快照携带 `release` + `generatedFiles`；每个生成文件的 `derivedFrom` 必须是图谱增量的子集，`generatedFrom` 字段锚定到带来该增量的快照（生成器交叉校验）——"代码实现了哪条需求"是数据，不是文案
- **沉淀与结构化设计**（携带它的世界才有，验收文档步骤 7-9）：`运行中`→`已完成(候选清单)`→`已采纳(图谱吸收)`，快照携带 `distillation`（候选 add/modify/remove + evidenceDoc 来源段落 + 采纳时刻 appliedAt）；采纳落位那帧，候选清单必须**等于**图谱波动（`check_distillation`：三组 target 对上 graphDelta 的 add/modified/removed 集合）——候选面板与图谱高亮不可能互相撒谎，"AI 改了什么、依据哪段文档"是数据不是黑盒
- **重生成与成组核对**（携带它的世界才有，验收文档步骤 10-11）：`已沉淀`→`已重生成`，快照携带 `regeneration`（新版本的 content + generatedFrom 指向那次沉淀）与 `diffGroups`（一组一业务点：userDiff/structuredChanges/regenDiff 三段）。重生成内容是沉淀事实的**函数**：细化行带被修改节点的新标签、新增行逐字复用候选 summary（`check_regen` 逐行校验）；三段里显示的每一行都是从本快照版本行的 unified diff 里按业务点关键词切出来的（预检重新切片逐字节比对），remove 组被禁止携带任何文档行——**空也是数据**，成组视图不可能展示快照没有的行
- **开发过程与结果**（携带它的世界才有，验收文档步骤 12-15）：`已重生成`→`开发中`→`开发完成`→`体验中`，快照携带 `devRun`（designVersion 锚定 `重生成版本 · graph@沉淀 id`；四阶段固定名 任务生成/编码实现/测试验证/构建打包，每个 done 阶段带一句事实摘要）与 `runPreview`（体验页数据）。**进度推进 = 载入过程快照帧，不是计时器**；`check_devrun` 每帧全量自检：完成⇔摘要非空、产物三件套与 runnableVersion 只能在全部完成后出现、体验页功能清单必须逐字等于图谱需求节点标签——「可运行」是数据不是文案。「打开可运行版本」是 overlay 内部帧切换（内置快照组件），**禁止起任何服务器/容器/真实部署**

迁移规则（脚本的每个 action 必须落在规则内）：

```
干净 --编辑(首次变更立即落记录)--> 草稿(+1条记录；此后输入停手2s防抖再落，内容与上条相同则不落新条)
草稿 --提交--> 已提交(vN+1；快照进 versions/，草稿记录清空；图谱 +Δ)
已提交 --发版--> 已发版(代码自图谱生成；每个文件标注来源图谱节点)
已发版 --沉淀--> 已沉淀(结构化事实候选→采纳→图谱吸收：新增/修改/移除)
已沉淀 --重生成--> 已重生成(结构化事实反向产出文档 vN+1，标注 generatedFrom；成组 Diff 三段按业务点核对)
已重生成 --开始开发--> 开发中(记录锚定冻结设计；四阶段推进靠快照帧)
开发中 --全部阶段完成--> 开发完成(产物三件套 + 可运行版本；完成前两者都不存在)
开发完成 --打开可运行版本--> 体验中(overlay 内切内置快照组件；无服务器/容器)
草稿 --恢复某条自动保存--> 草稿(当前内容=该条)
已提交 --编辑--> 草稿
```

页面只是状态的展示；脚本先改状态机，再对页面。

## 三、演示步骤 = 业务事件，不是按钮动作

每个 Step 的统一结构（事件 + 状态迁移 + UI 反馈 三件套）：

```json
{
  "id": "s2",
  "title": "编辑需求文档后，自动保存生效",
  "branch": null,
  "fixture": "main-004",
  "before": { "doc": "requirements.md", "diffIcon": "gray", "draftRecords": 0 },
  "action": { "event": "用户追加一行验收标准，首次变更立即落一条草稿记录" },
  "after":  { "diffIcon": "active", "draftRecords": 1 },
  "highlight": { "target": "[data-testid=doc-requirements.md]", "hint": "图标亮起：存在未提交的自动保存", "open": [] }
}
```

### 七字段验收结构（T10 落地）

出处：《AI-Coding 平台-验收文档》(`raw/AI-Coding平台-验收文档.zip`) 的统一步骤
结构——**从哪里开始 → 用户做什么 → 去了哪里 → 用户看到什么 → 页面有什么变化 →
后台发生什么 → 怎样算通过**。三件套不推翻，七字段吸收进来（`startFrom` /
`userAction` / `goesTo` / `userSees` / `backendFact` / `passCriteria` 六项新键，
「页面有什么变化」即既有 before/after，不存第三份）：

- **派生拼装，不手写第二份事实**：`userAction`/`userSees` 逐字复用既有事件与
  提示；`startFrom` 是 before 观测的渲染；`goesTo` 按高亮目标查视图表；
  `backendFact` 由前后快照的观测差派生；`passCriteria` 由 after 观测逐项生成
- **双重消费**：生成时 schema 预检逐条校验（缺字段/判据与 after 不符 →
  fail-fast 指明字段名）；剧本测试对每条判据在业务 DOM 读数上逐条兑现——
  验收文档展示的"怎样算通过"和测试跑的判据是同一份数据
- **向后兼容**：三件套字段全部保留，快照不变；T11-T14 的新步直接按七字段写

## 四、演示必须有"视觉引导层"

- 每步给 **高亮目标**（selector + 描边）与 **当前提示文案**（"当前：请查看 diff 图标的红绿行"）
- 引导层是**独立的 overlay 组件**（高亮框、提示条、上一步/下一步/自动播放的步进器），演示模式由 URL 参数 `?demo=<剧本名>` 注入——**业务组件内不许出现任何"为了演示"的代码**
- 弹层/菜单的展开也是引导层的事：脚本说"现在该看修改历史面板"，引导层负责把它打开并指过去（`highlight.open` 的 selector 序列按序程序化点击）

## 五、演示不改真实数据：状态快照，可回放

- 每个 Step 携带一份完整状态快照（`fixtures/state-*.json`），对应后端 store 的一份数据（演示模式下把数据层指向快照 fake，fetch 一个都不发）
- 下一步 = 加载 State(n+1)；上一步 = 加载 State(n-1)；**禁止反向计算/反向操作恢复**
- 演示全程写独立 home（`KIROCREW_HOME` 指 demo 目录），**绝不碰用户/演示环境的真实项目数据**

## 六、状态层与展示层分离（回放稳定性的根）

- **状态层**：现在有哪些文档/草稿/版本、内容是什么——快照驱动
- **展示层**：现在高亮什么、提示什么、该开哪个面板——剧本驱动
- 禁止 `step 执行 → 改数据 → setTimeout 开弹窗` 的耦合写法（回退残留、自动播放冲突、CDP 不稳三坑都源于它）
- 回退 = 状态层整体换快照 + 展示层按该步剧本重放，两者各自幂等（实现上：每一步都整体换装——数据层载入快照、工作台按步号重挂载、引导层重放该步的 `open` 序列——重复进入同一步必然得到同一画面）

## 七、必须覆盖异常分支，不止 happy path

AI Studio 至少要演：

- 无修改时 diff 图标置灰不可点（为什么灰 → 状态机里"当前==最近提交"）
- 修改历史为空（刚提交完）——顺便讲"提交即清空"的规则
- 最早版本无上一版 → diff 整篇为新增
- 从一条自动保存记录**恢复**的分支（草稿态回到过去）

分支步骤与主线共用同一套 Step 结构，剧本里标 `branch: "alt-N"`。

## 八、剧本测试测的是剧本，不是页面

剧本测试（`website/src/apps/ai-studio/demo/demoScript.test.tsx`）必须验证四件事（"按钮存在/文字存在"级别的测试不算数）：

1. **状态迁移**：执行 step 后 before/after 声明的状态逐项为真（DOM data 属性或 store 断言）
2. **引导落位**：当前步的 highlight selector 命中且可见
3. **回放一致**：手动"下一步"×N 的最终状态 == 自动播放到第 N 步的状态
4. **回退恢复**：走到 step5 → 上一步 → 页面与快照 State4 完全一致（最容易出 bug 的一处）

测试跑在演示模式 + 独立数据 fake 上；CDP 调用一律带 timeout 与总闸。

## 九、标准目录结构（本仓库的实际落地）

```
website/src/apps/ai-studio/demo/
  scenario.md                # 业务故事线（人读的剧本说明书）
  steps/*.json               # 步骤剧本（三件套结构，三条线）
  fixtures/*.json            # 每步状态快照（generate_fixtures.py 生成，保证与后端 difflib 语义一致）
  generate_fixtures.py       # 快照与剧本的生成器（改动文档内容后重跑）
  types.ts                   # Step / 状态快照的 schema
  runtime.ts                 # 演示运行时：?demo= 解析、快照 fake 数据层、步进状态
  overlay.tsx                # 视觉引导层（高亮框/提示条/上一步/下一步/自动播放）
  demoScript.test.tsx        # 剧本测试（上面四项断言）
docs/guides/ai-studio-demo-methodology.md   # 本方法论（登记进 docs/README.md 索引）
```

## 十、示范剧本（本仓库的三条线）

- **主线 `?demo=main-membership-points`「会员积分系统」**（21 步）：进项目 → 版本历史看 v1 整篇新增、v2 增量 diff（含"返回编辑"）→ 回编辑器改两行 → 首次变更立即自动保存落记录 → diff 图标亮起 → 打开红绿 diff → 提交 → 修改历史清空、版本历史 +1、图标回灰 → 图谱亮起本次提交新增的需求节点 → 点发版：AI 按图谱生成代码，每个文件标注来源需求节点 → 点开始沉淀：AI 把冻结文档沉淀为结构化事实（候选清单注明来源段落）→ 采纳后图谱吸收并高亮新增/修改/移除 → 重生成文档 v4（标注来自哪次沉淀）→ 三段成组 Diff 按业务点核对"系统理解得对不对" → 点开始开发：开发记录锚定冻结设计，四阶段靠快照帧推进到全部完成（产物三件套 + 可运行版本）→ 打开可运行版本：overlay 内切到内置体验组件，功能清单恰好等于图谱需求节点（需求→图谱→代码→沉淀→重生成→开发→可运行的闭环在收官镜头合龙）
- **分支 A `?demo=alt-1-draft-restore`「App 官网改版」**：有未提交草稿 → 打开修改历史列表 → 挑较早一条看 diff 并**恢复**（草稿态回到过去）→ 恢复后的文本再被防抖记为新一条
- **分支 B `?demo=alt-2-empty-gray`「空项目示例」**：三个图标全灰态，逐步解释"为什么是灰的"（diff 灰 = 当前==最近提交；修改历史灰 = 提交后清空；版本历史灰 = 从未提交）

## 怎么打开演示

1. 用**独立 home** 起网关（演示环境隔离，不碰真实数据）：

   ```bash
   KIROCREW_HOME=/tmp/kiro-demo-home python3 -m kiro_crew gateway   # 按需换端口
   ```

2. 往网关里灌演示项目数据（或直接复用 `fixtures/*.json` 里的 `project`/`docs` 经 API 创建）。
3. 浏览器打开 `#/ai-studio/projects/<项目id>?demo=main-membership-points`（剧本名对应 `steps/<剧本名>.json`）。命中演示模式时：数据层由快照 fake 接管（不发任何 fetch、写操作只动内存），右下角出现步进器；未带 `?demo=` 时页面行为与平时完全一致。
