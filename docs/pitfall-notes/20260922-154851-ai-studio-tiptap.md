# AI Studio 可视化文档编辑器：Tiptap 三坑

把 docmost 那种所见即所得文档编辑器做进 ai-studio builtin app（`website/src/apps/ai-studio/`），
数据格式保持 Markdown。三个坑，每个都是"看代码看不出来、跑起来才知道"的。

## 背景：为什么是 Tiptap，不是搬 docmost

docmost 的编辑器底层就是 Tiptap（ProseMirror 之上），但 docmost 是 **AGPL-3.0**，
把它的代码抠进这个 Apache-2.0 公开仓库等于把 copyleft 带进来。Tiptap 本体是 MIT，
同一套引擎、干净的来源。`packages/ee/` 那类企业版目录更是碰都不能碰。

## 坑一：`@tiptap/markdown` 没有默认导出（最疼的一个）

**现象**：编辑器渲染出来是纯文本——`# 需求说明` 连标题带井号原样显示，工具栏全灭，
但**不报任何错**。

**根因**：习惯写法 `import Markdown from '@tiptap/markdown'` 拿到的是 `undefined`。
这个包只出具名导出（`Markdown` / `MarkdownManager`），它的 barrel 压根没有
`exports.default`。`undefined` 混进 `extensions: [...]` 后被扩展管理器静默丢弃，
`contentType: 'markdown'` 找不到 Markdown 扩展，初始化解析整段跳过——
于是 Markdown 字符串被当 HTML 兜底解析成了一段纯文本段落。

**排查姿势**（这是唯一快速的路）：写一个最小探针测试挂 useEditor，在 `onCreate` 里查
`editor.extensionManager.extensions.find(x => x.name === 'markdown')`——
返回 `MISSING` 直接锁死根因。探针让它 `throw` 把值带进断言失败信息，比 console.log
在 vitest 里可靠（本仓库 vitest 配置会吞 console 输出）。

**修法**：`import { Markdown } from '@tiptap/markdown'`。

**教训**：Tiptap 3 生态里 starter-kit 有默认导出、markdown 包没有，两种风格混着用。
接一个 tiptap 包先 `grep exports.default dist/index.cjs` 看一眼，10 秒省一小时。

## 坑二：ChatEmbed 对不存在的槽直接 404，聊天栏开局即死

**现象**：ai-studio 左栏用 app-sdk 的 `ChatEmbed` 嵌原生聊天，新浏览器 profile 首次打开，
聊天区不是空会话而是错误条"无法加载此会话的消息"，且没有自愈路径。

**根因**：ChatEmbed 挂载就读 `GET /api/chat/slots/{slotKey}`，**槽不存在返回 404**，
embed 把它渲染成 loadFailed 错误条。"用户发第一条消息时后端会自动建槽"是对的
（`POST /api/chat` 的 auto-create），但那个自动建槽救不了首次的 GET——GET 先失败，
错误条先挂出来。

**修法**：挂载聊天前先 `POST /api/chat/slots` 幂等建槽（design-critique / design-tweak
都是这个惯例）：带显式 `name` 时后端对手已存在的槽原样返回（不是报错）；且 app token
建的槽会打上 `_app` 归属，这才过得了后续 GET 的跨 app 隔离检查（`_deny_cross_app_slot_access`，
否则别的 app token 反而能 404 你的槽）。建槽 settle 之后再挂 ChatEmbed，避免 GET 抢在 POST 前。

**顺带**：外层 `AppScopedApiProvider` 的 `navigateFn` 传行内箭头函数的话，每次父组件
渲染都是新引用 → scoped-api context 值变 → 依赖 `api` 的 effect 反复重跑（表现为
重复 POST 建槽）。包一层 `useCallback` 固定住。

## 坑三：Raw/富文本双模式下，编辑器实例跟着视图走，不能"一个编辑器扛两个模式"

**设想**：一个 useEditor 实例长驻，切 Raw 模式只是把 `<EditorContent>` 藏起来。

**实际**：`EditorContent` 卸载再挂载后，ProseMirror 手里的 element 已经离开文档树，
再切回来编辑器就废了。@tiptap/react 的 `EditorInstanceManager` 用
`scheduleDestroy`（1ms 定时器 + isComponentMounted 复查）处理卸载，这个宽限期是给
"StrictMode 双挂载/重渲染"准备的，不是给"卸载几秒后再回来"准备的。

**修法**：每次模式翻转 `setGen(g => g + 1)`，把 `[gen]` 作为 useEditor 的 deps——
deps 变了管理器就 destroy 旧的、用最新 options 建新的；翻转 handler 先把当前内容
（`editor.getMarkdown()` 或 Raw 缓冲）写进一个 ref，新实例创建时从 ref 取初始
content。`contentType: 'markdown'` 时初始 content 就是 Markdown 字符串，官方扩展
在 `onBeforeCreate` 里解析，不需要自己转 HTML。

**注意 deps 语义**：useEditor 的 deps 数组非空时**跳过** options 的浅比较增量更新、
走整实例重建，所以 deps 里只放"翻转"这种低频信号，别把内容/文档 id 放进去，
否则每敲一个字重建一次编辑器。

## 测试侧配套（happy-dom + Tiptap）

- 编辑器在 effect 里创建（`immediatelyRender: false`，SSR 安全默认），所以首屏断言
  必须 `await screen.findBy...`，`getBy` 会抢跑。
- 别用 `findByRole('textbox')` 等编辑器就绪——happy-dom 里 contenteditable 的
  role 映射时好时坏；等一段渲染出来的文本（如 fixture 的标题）更稳。
- 工具栏按钮断言只断"跑了不炸 + aria-pressed 存在"，不断 ON/OFF 对称：在 H1 上点
  Heading1 是"转成段落"，第二次点的 pressed 值取决于光标语义，是脆断言。
- 浏览器端 CDP 验证时注意：本仓库 dev 域名走 vite 按需编译，首开常 502/模块加载失败，
  重试 2~4 轮预热即好，不是代码问题。
