# 自建的 dnt 近邻拼写检查把进程吃到 13 GB 被内核杀掉

时间：2026-10-10 18:37 前后
相关：`scratch/acp2113-gap/checkgap-full.py`（被杀的那版）、`checkgap-safe.py`（改写后）

## 现象

自己写的分片核验脚本 `checkgap-full.py` 跑 `hi` 语种，**没有任何 Python 异常、没有
traceback**，进程直接消失。`dmesg` 里是 OOM killer 的记录，被杀时 RSS 已到 13 GB。
同样这段代码在 `bn`（13 键）上跑得好好的，换到 181 键就死，第一反应像是「键多了所以
慢」，但它不是慢，是内存爆炸。

## 根因

那 62 个 do-not-translate 词的近邻拼写检查是这么写的：

```python
for t in dnt:
    for m in re.finditer(re.escape(t.lower().replace(" ", r"[\W_]*")), low):
```

意图是「允许词内插标点」，于是把 `product` 编译成 `p[\W_]*r[\W_]*o[\W_]*d[\W_]*u[\W_]*c[\W_]*t`。
问题出在 `[\W_]*`：

1. **`\W` 匹配任何非词字符，包括每个天城文字符**（Devanagari 字母不是 `\w`？它是；
   但 matra、nukta、空格、`{{`、`…`、`-`、`/` 全是 `\W`）。一条译文里连续几十个
   `\W` 位置，六七个 `[\W_]*` 串在一起，就是组合爆炸的输入。
2. **`re.finditer` 是 NFA 回溯**，没有匹配上限也没有超时。当整词根本不存在时
   （181 条里大多数 dnt 词都不在），引擎要把每种切分方式都试完才回答「没有」。
   多个 `[\W_]*` 相邻时可切分的长度是乘法关系，指数级。
3. 每个位置的失败路径上，`re` 都在 C 层持有回溯栈；外层还套着 `181 键 × 62 词`，
   所以内存不是一点点涨，是某几条长译文一进去就几十倍地跳。

`bn` 那 13 条恰好短、且恰好命中/不命中都落在浅层，所以没触发。这不是语种差异，是
样本大小的运气。

## 修法

**不要给这个规则加更多正则层**。改判定方式，把「允许词内插标点」变成字符串预处理：

```python
low = v.lower()
for t in dnt:
    tl = t.lower()
    if tl in low:
        continue                       # 正确写法，放过
    compact = re.sub(r"[^a-z0-9]", "", low)     # 一次性摊平，线性
    if len(tl) > 3 and re.sub(r"\s+", "", tl) in compact:
        problems.append("dnt 词在，但被改了拼写/加了内部空格")
```

`compact` 每条值只算一次，然后 62 次都是普通子串查找。181 键从「被 OOM 杀」变成
0.4 秒。语义上和原来等价，而且更准：原来 `[\W_]*` 连「词与词之间本来就有的空格」
也算进去了，会把 `AI Studio` 判成 `A.I. Studio` 的近邻拼写。

## 怎么避免

- **`X*` 挨着 `X*` 的正则就是雷**，尤其是 `\W`、`\s`、`.` 这类「什么都能吃一点」的
  字符类。写的时候问一句：不匹配的最坏情况要试多少种切分。
- **给任何跑在「别人写的文本」上的正则加超时或改线性算法**。译文、用户输入、日志都算
  别人写的文本 —— 里面出现长标点串、成对括号、连续非 ASCII 的概率远比源码高。
- **进程静默消失先查 `dmesg`**，不要在脚本里加 print 找「卡在哪一行」。没有 traceback
  的死亡基本是外部 SIGKILL（OOM）或 C 层崩溃，Python 层的日志帮不上。
- **自建检查器要用最坏样本试**，不要用最小样本。我拿 13 键的 bn 验过就认为它可信，
  结果它唯一没验过的恰恰是「量大 + 长文本」这个维度。
