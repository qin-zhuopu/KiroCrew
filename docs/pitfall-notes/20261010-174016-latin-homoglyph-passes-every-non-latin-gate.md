# 我手打的俄语里混进了拉丁同形字，两道门全绿 —— 而且我先把这个现象编成了「通道坏了」

时间：2026-10-10 17:40
相关：ACP-2113（ru 补漏 13 键）、本仓 `docs/pitfall-notes/20261010-161723-*`（压缩后编造指令，
同一类错的另一种形态，本篇是它的续）、`docs/pitfall-notes/20261010-010657-*`（同一道「照屏幕重打」
检查的三种**别的**失效方式：词形门看不见屈折、双胞胎码位规则会把意思改反、n-gram 门定不了罪。
本篇补第四种：**拉丁冒充西里尔，结构上没人看得见**）

## 现象

我给 `team-lead` 发的交付回报里写着 `Проверяem...`，让它去查这个键时，肉眼和它一模一样。
码位一摊开就知道错了：

```
真：Проверяем...   е = U+0435 CYRILLIC SMALL LETTER IE
我：Проверяem...   e = U+0065 LATIN SMALL LETTER E   ← 我手打时打进去的
                   m = U+006D LATIN SMALL LETTER EM  ← 同一个词里错了两个字符
```

我发的 4 条回报正文里共 112 个含西里尔的 token，**4 个带拉丁同形字**，全是同一个词
`Проверяем`（因为我为了说明省略号问题反复手打了它 4 次）。
**同一批经过程序化搬运的交付文件 `ru/shard-01.json` 是干净的**：全文件 ASCII 字母只有
`{{n}}`、`{{time}}`、`lint`，没有任何拉丁字母贴在西里尔旁边。

## 根因一：那道「防假西里尔」的门结构上看不见拉丁字符

`check-vocab.py` 的字符档不是「检查字符集是否合法」，是
**只遍历目标文字区间内的字符，逐个查它在不在批准词表里**：

```python
RANGES = {... "ru": r"Ѐ-ӿ", ...}
native = re.compile(f"[{rng}]")
for ch in native.findall(value):        # ← 区间外的字符根本不进循环
    if ch not in vocab_chars:
        bad_chars.append(...)
print("  character coverage: OK (no native script invented)")
```

拉丁字母在 `Ѐ-ӿ` 之外，**一次都不会被取出**，所以「拉丁冒充西里尔」是这道门的一个结构性
盲区。实测（我用 `str.maketrans` 程序化造污染样本，不手打，避免用可能已经坏了的通道自证）：

| 污染样本 | 字符档 | 仓里真判据 `checkValue()` |
|---|---|---|
| `е`→ASCII `e`（`Провeряeм`） | **OK / exit 0** | `[]` 无 finding |
| `о`→ASCII `o`（`Прoверяем`） | **OK / exit 0** | `[]` 无 finding |
| `и`→乌克兰语 `і`（`Поручіть`） | HARD FAIL `U+0456` / exit 1 | `[]` 无 finding |

第三行是关键对照，说明**这道门的判据严格来说是「字符是否落在西里尔区块内」，不是
「字符是否属于俄语」**：跨区块的同形字（乌克兰语 `і`、白俄语 `ў`）会被抓住，
而跨文字的（拉丁冒充）永远漏网。

**更要命的是那句成功文案**：`character coverage: OK (no native script invented)`。
它字面上是真的——它只断言「没有臆造出本民族文字之外的字符」。
读起来却像「这个文件的俄语没问题」。我第一遍读到它就停了。

仓里的 `checkValue()` 同样漏（三种污染全部 0 finding），所以这不是我自造工具的问题，
**没有任何一道现有门会红**。只有母语者看得出来。

## 根因二：查无对证时，我给一个不存在的现象编了一条「传输链路坏了」

发现同形字之后，我「回想」起 `team-lead` 某条**发进来的**消息里
`ассистенту` 被写成了拉丁转写，于是宣布「SendMessage 通道会腐蚀西里尔文」并准备上报。

grep 实测：**那条消息整条不存在**。

```
那个拉丁转写串   在我自己那份 transcript 里 11 次命中，全部是 assistant role（我自己写的两句文本）
                 team-lead 发给我的 13 键任务书里 0 命中
相关俄文原词      team-lead 消息里 0 命中
```

也就是说：拉丁同形字这个**现象是真的**（它确实在我打的字里，见上），
但我给它编的**成因是假的**——不是通道丢的，是我自己手打进去的。
我把「我找不到它的来源」当成了「传输丢了它」。

## 修法

1. **非拉丁文字只能程序化搬运，不能手打**——这条我一直知道，这次是我自己违反应用它自证。
   写进回报正文的俄语，也要从文件读出来再插进去，不要在正文里重打一遍
2. **自查用「拉丁字母是否紧贴西里尔」这个判据**，不要只跑 `check-vocab.py`：

   ```python
   any(ch.isascii() and ch.isalpha()
       for ch in s
       if any('CYRILLIC' in unicodedata.name(c,'')
              for c in (prev_of(ch), next_of(ch))))
   ```
   `ru.json` 全量扫这个判据 = 0 命中，所以它可以当常规门用，不会天天误报
3. 已经向 `team-lead` 发了撤回：撤掉「通道腐蚀西里尔」这条结论，并明确
   **别从我消息正文里复制那个词**，要用从文件读

## 怎么避免

- **一句成功文案的作用域，比它读起来的作用域窄**。
  `no native script invented` 只说了它字面那件事。看到 `OK` 之前先问：
  **这句话在断言什么，我拿它当成了在断言什么**——这两者的差就是我漏掉的东西
- **「链路/工具/传输坏了」是需要正向证据的断言**：要能同时拿出坏的那份和好的那份，
  指得出写入端和读出端。**「我这边找不到」永远推不出「传输丢了它」**。
  我这次只要先把搜索对象对准自己那一份 `subagents/agent-*.jsonl`（见
  `docs/pitfall-notes/20261010-150459-*`），第一秒就会发现词是我自己打的
- **自造污染样本要用 `str.maketrans` 之类程序化手段，不要手打**。
  要验的正是「我的字会不会坏」，用手打来自证等于用待验通道验待验通道。
  我第一次的 `і` 样本就是个 no-op（那句俄文里根本没有 `и`），差点据此报一条假发现
- 我第一版报告里那句「`AI Studio` 这批 13 句英文里根本没出现，无音译风险」是真结论
  （DNT 62 词在我值里 0 命中）——**同一份报告里真结论和假成因会挨在一起**，
  有一条查过不代表整段查过
