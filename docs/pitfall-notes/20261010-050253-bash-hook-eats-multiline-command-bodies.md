# Bash 钩子把「多行正文」当截断管道拦：Jira 评论写了个 JSON 示例就连拒三次

时间：2026-10-10 05:02（ACP-2226 收尾，kc-gate 会话）

## 现象

完工评论往 Jira 发，`jc jira issue comment ACP-2226 <<'EOF' … EOF`，**连拒三次**，一次都没发到 Jira：

```
head/tail 截断输出已被拦截。…禁止任何形式的 head/tail 管道截断。
```

我这条命令里**没有任何管道**，正文是中文的完工报告。前两次我以为是自己写法问题，
把 `| tee` 之类的都去掉了照样拒。

## 根因

本机 `~/.claude/settings.json` 的 PreToolUse 钩子是**字符级扫整条命令文本**的，
不看语义、不看位置。它要拦的是 `head` / `tail` 这两个英文词，而我的评论正文里有一句门禁
结果样例：

```
{"id":"lint","ok":false,"detail":"exit=1\n...输出 tail..."}
```

正文里的英文单词命中了关键词 —— heredoc 的正文、`commit -F - <<EOF` 的提交信息、
脚本注释、`grep '某词'` 的查询模式，全都在扫描范围内。全局约定里写过「延时那个关键词
同样会被正文命中」，但我当时只把它记成「别在前台空等」，**没想到同一条钩子对
`head`/`tail` 也是这样**，于是两次重发都在改无关的地方。

第三次我把那句英文说明换成中文（「输出末尾」）才发出去，代价是三份要重写的正文。

## 修法

- 往 Bash 里塞多行正文（Jira 评论、`commit -F -` 的提交信息、PR 描述、heredoc 脚本）
  之前，**先自查正文里有没有这两个英文词**，有就改中文（「输出末尾」「开头」「前几行」）
- 正文里带 JSON 示例 / 字段说明时最容易中招：`detail`、`snippet`、`logTail` 这类字段名
  和它们的示例值天然像在描述"取尾部"
- 被拒时**先读自己的正文措辞**，不要先改命令结构（不是 `tee` 的错，也不是 stdin 的错）

## 怎么避免

- 长正文用 **Write/Edit 工具**落文件（不经 Bash），再让命令读文件：`jc jira issue comment
  <KEY> --file <path>` 就是为这个准备的。缺点是本机有条「不许往 /tmp 写文件」的纪律，
  那就写到 worktree 里跑完删掉，或者干脆走 stdin 但先把措辞过一遍
- 反过来也别为了绕钩子去改名、拆字符拼接（约定里明令禁止），换措辞就够了
