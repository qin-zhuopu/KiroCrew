# 非拉丁文种的「照屏幕重打」检查：三个门各自以不同方式失效

补 `apps.aiStudio.*` 其它语种（ACP-2113 范围，237 键 × 9 语种）时，天城文/孟加拉文
只能从已批准目录里程序化搬运 —— 照屏幕重打会写出**码位不同的假词**（anusvara 与
candrabindu、nukta、元号位置），肉眼看两遍都是同一个「对」的字形。所以我写了三道门
来抓这种错。三道门都跑了，每一道都以不同的方式失效，其中两道比我原本担心的错误更糟。

事实结论先放前面：**唯一有用的门是「我自己也不判断拼写，只搬运码位」**；
所有「自动判出拼写对错」的门，最后只能做**排序**，不能做**定罪**。

## 现象

孟加拉文候选 237 个值，词形门报 43 条 `SUSPECT_TRANSCRIPTION`。里面确实有一条真错
（`সংস্করণ`「版本」被写成 `সংস্করেন`，多一个 U+09C7，影响 12 个值），但它混在 43 条里，
和 42 条正常变格长得一模一样。真错在批准目录里 0 条命中、正字 86 条值命中，本该一眼可辨。

## 根因一：词形门看不见屈折

门的判据是「候选里每个非拉丁 token 必须逐字节出现在批准目录里」。批准目录里有
`গ্রাফ`（graph），但我的值写 `গ্রাফে`（**在图里**，加位置格后缀）。token 不等 → 报嫌疑，
而且打印出来的**码位差异是空的**（`差异 []`）—— 一个「有差异所以可疑」的门给出了零差异的
嫌疑，这本身就是它失效的信号。孟加拉文靠后缀屈折，批准过的词干不构成对它任何变格的许可。
同类误报还有 `ডিজাইনের`（of the design）、`রিকোয়ারমেন্টে`（in the requirement）。

## 根因二（最贵的一道）：「差一个码位的双胞胎」规则会把意思改反

为了让门能定罪，我加了规则：批准目录里查无此词 + 与某批准词**同辅音骨架且只差一个码位**
⇒ 判为错拼。它确实抓到了 `সংস্করেন`，同时判错三个**正确的词**：

| 我的词 | 意思 | 规则建议的词 | 意思 |
|---|---|---|---|
| `খোলেনি` | 没有打开 | `খোলেন` | 打开 |
| `ডিজাইনের` | 设计的（属格） | `ডিজাইনার` | 设计师 |
| `চলানো` | 去运行 | `চলুন` | 请来 |

第一条是意思取反 —— 门会把正确的译文改成错的陈述。根因：**「批准目录里没出现过」
不等于「写错了」**，它只说明这个目录恰好没写过这个短语。把「没证据」当「反证」，
就是一个能改反语义的规则。这种规则比没有规则更糟，因为它给出可执行的结论。

## 根因三：n-gram 门也定不了罪，而且连正字都会命中

设想一个不需要懂孟加拉文的正字法 oracle：把批准目录切成 n-gram 索引，我的 token 若含
批准目录里查无的 gram 就可疑。跑 3-gram/4-gram 都不行：

- 词干与后缀**接缝处**的 gram 对正常词也是未经批准的（`প্রস্তুত` 相关形态命中 `ন্তু`）；
- 拿正确的 `সংস্করণ` 单独测，它自己也有一段 gram 在目录里查无（`রণ`）。

也就是说这个门的假阳率接近 1，只能用来**排序**（把可疑的排前面给人看），不能用来判红。
我差点把它接进交付判据，是那次自测（拿批准词本身测）拦住的。

## 修法：判定归人，字节归机器

最终形态（`bnfix1.py`，脚本与需求文档已归档到 jereh-cli 的 requirements 目录）：

1. 我把**错的和正确的拼写都写成 ASCII 码位数组**（`[0x09B8, 0x0982, ...]`）。
   终端能重排字形，重排不了我手打的十六进制数 —— 这是唯一我能安全提供的信息。
2. 写盘前先在批准目录里断言「正确写法的码位序列存在」，不存在就直接拒。
3. 后缀也按码位钉住并**按长度倒序替换**（`...ের` 必须先于 `...ে`，否则会生成叠字）。
4. 替换后逐个校验新生成的**每个变格形态**都是某条批准值的子串；查不到的打出来，
   不假装整族已修好。

配合两条机械门，交付才算完：

- **仓库真门**（`gatecand.mjs`）：`npm run i18n:check` 读的是仓内目录，候选不装进去就
  什么都不告诉你。但 `check-source-strings.mjs` 的 Pass 2 与 passthrough 那半边都把判据
  导出成了纯函数（`changedValueFindings` / `passthroughFindings` / `checkValue`），
  拿仓内目录当 merge base 直接调用即可 —— 装进树之前就知道这些值会不会让 CI 红。
  `checkValue` 还带 `placeholder-parity`，是前两个门看不见的那一类：译文翻得再好，
  丢了 `{{name}}` 一样是运行时故障。
- **本批一致性门**（`internal.py`）：同一个英文值在我这 237 键里必须同一译法。
  这一门是我原本**没写**的门，它一次抓出 18 处（`Running` 在 ru 里两种写法等），
  全部按批准库多数写法统一（`fixcons.py` 每处打印它的证据键与实测计数）。
  合法的差异必须进 `EXEMPT` 并写理由：`Freeze` 在确认按钮上是祈使（去做），
  在历史条目里是名词（做过的事）—— 强行统一在每个语种都是错的。

## 怎么避免

- **非拉丁文种：不允许任何环节出现「人/模型照着屏幕重新打一遍字」。** 值只能从文件里
  `read` 出来再 `write` 进去；我要表达选择时，只给码位数（ASCII），不给字形。
- **自动门先分家：「排序给人看」和「判红」是两种门。** 写一个新判据时，第一件事是
  拿**批准目录自己的值**喂它，要求 0 命中；喂不进去就说明它会误伤，最多当排序用。
- **「查无此词」永远不是反证。** 任何以「批准目录里没出现过」为唯一依据的规则，
  都先问它会不会把一句话的意思改反（`খোলেনি` → `খোলেন`）。
- **嫌疑清单里出现「码位差异为空」= 门在误报**，不是「可疑但说不清」；先修门再读清单。
- 大批量翻译**必须有一道「同批内自比」的门**：批准库对照只能发现历史漂移，
  一批 237 键内部自相矛盾是另一种缺陷，只有自比能抓到。
- **工具链自己也要有「故意放一个错」的阳性对照。** 我留了一份 `out/poison/`：把
  `{{n}}` 打成 `{n}}` 的坏候选。它在 `gatecand.mjs` 上确实报红（门是活的），但
  把它拿去跑仓库的 `i18n-translate.mjs verify` 却一个字都不报 —— 因为 `verify` 只
  认 `<dir>/en/shard-*.json` + `<dir>/<语种的>/shard-*.json` 这种分片目录，喂给它
  一个装整份目录的文件时，`readdirSync` 找不到分片，`shards=[]`，于是打出
  「0 shard(s), 0 key(s), 0 finding(s)」当作通过。**没读到的分片不会报错，只会变成
  好看的 0**。凡是「跑完报 0 个问题」的检查，先问它读到了几个对象；`0 key(s)` 和
  `0 finding(s)` 同时出现就是废火，不是绿灯。
- 拿批准库做「意思对不对」的对照时，**别按整条英文去比**：`Complete` 一个词在批准库
  里既可能是按钮（动词「完成」）也可能是状态（形容词「已完成」），逐行看会把位置差异
  当成语义错误。先按键名后缀分类（`*_toast`=句子、`*_kind_*`/`*_phase_*`=标签、
  `*_ok`=按钮），只在同类里比 —— 46 处差异里这样一审只剩下个位数需要人判。
