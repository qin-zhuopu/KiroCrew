# 同一提交重复点部署，版本号一路涨（v3~v7 是同一份代码）

日期：2026-10-10　单子：ACP-2219　文件：`src/kiro_crew/apps/builtins/ai_studio/backend/prodserver.py`

## 现象

「设备管理」工作区，同一份代码（`d9d530d9`）连点 5 次〔重新部署〕：版本从 v3 涨到 v7，
个人仓上多了 5 个标签（`v3`…`v7` 指向同一个提交），发布台账 5 条。部署每一步都是绿的，
一个报错都没有 —— 所以它不是故障，是从没人为「代码没变」这种情况写过规则。

## 根因

版本号是**算出来的**，不是记下来的：

```python
n = len(publish.list_release_records(project_id)) + 1
```

发布台账记几条，版本号就涨到几。于是「不升版」这件事在这份代码里没有落点：想让它不升，
就必须**同时**不让它记台账 —— 而这两件事原本分别在两个地方：算版本号在入口
（`deploy()` 里 `_next_version()`），记台账在成功那步（`_succeed()` 里 `_record_release()`），
中间隔着七步、隔着一次可能失败的探活。

**这就是这一单真正的坑**：它不是一个 if 的事。在成功那步加判断（「和上一条比一下，一样就别记」）
会当场自相矛盾 —— 版本号在入口已经按「条数 + 1」算成 v4 了，中途不记台账，下一次部署算出来
还是 v4，而 v4 这个标签在上一轮已经打出去了（`git tag` 报 already exists，且界面上顶栏显示的
版本号是从状态文件读的，用户看到的和他以为的不是同一个东西）。

## 修法

把「这一版是几号 + 要不要沿用旧号」合成入口的**一个**决定，再把结论一路带到成功那步：

- `deploy()` 读一次 HEAD，交给 `_version_plan(head)` → `(版本号, 是否沿用)`；
  最新那条台账的 `commitHash` == 本次 HEAD → 沿用它的版本号。
- 沿用结论作为参数穿过 `_start_deploy` / `_deploy` 到 `_succeed`，那里跳过打 tag / 推 tag /
  记台账，只写一行日志「代码没变，沿用版本 vN」。
- 正式实例照常走完整的构建 → 停旧 → 起新（用户点〔重新部署〕要的就是重启，不能顺手跳过）。

两处顺带处理：

1. **台账是外部文件**：沿用之前要验它里面的版本号还是 `v<N>` 形状。一个手改出来的 `v1.0`
   照字面沿用，会在拼域名那次校验里抛 `bad_version` 400 —— 部署按钮直接点不动，直到有人去
   手改台账。退回按条数 +1，代价只是这一版升个号。
2. **HEAD 只读一次**：`_acceptance()` 原本自己去 `rev-parse HEAD`。分两次读，两次之间工作区
   里落一个新提交，就会「按旧提交决定沿用、按新提交过验收」，一个部署里两个 HEAD。

## 怎么避免

- **一个派生值只由一处算，改它的规则也只能在那一处。** 「版本号 = 台账条数 + 1」这件事一旦
  和「什么时候记一条台账」分属两个时机，任何一半的单独修改都会造出一个自相矛盾的中间态。
  下次要加〔升版〕按钮（ACP-2205）同样是从 `_version_plan` 出口走，别在成功那步补判断。
- 判据要用真存储：`test_redeploying_the_same_head_keeps_the_version` 用 `real_ledger=True`
  写穿到真实台账，断言的是「条数没长」。「没多记一条」这件事用假 recorder 怎么接都能过。
- 顺手钉一条反向断言：沿用一次之后**再换提交**部署必须是 v2 而不是 v3，否则「沿用」只是把
  升版往后推一格，测起来和修好了一样绿。
- 台账和标签都是「一次部署一个身份」的记账，重复记账不会报错，只会让账本没法看。凡是
  「成功后追加一条」的路径，都值得先问一句：这次成功后，东西真的变了吗。
