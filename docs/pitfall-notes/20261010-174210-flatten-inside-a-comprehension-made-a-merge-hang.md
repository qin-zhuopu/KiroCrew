# 「老键零改动」断言写在推导式里，每次比较都重摊平一遍 1.5 万键目录

日期：2026-10-10 17:42（ACP-2113 合并脚本）

## 现象

自己写的合并脚本（把分片并进 `locales/<语种>.json`，1.1 MB / 1.5 万键）跑不完：

- 前台 30 秒超时被移到后台
- 杀掉、改成单语种再跑 `time`，**还是**超时
- 没有任何报错，没有任何输出——连第一行 `print` 都没打出来

第一反应是「读文件慢」或「卡在 git 上」，都不是。

## 根因

自查用的那行断言：

```python
changed = [k for k in before & after if flat(catalog)[k] != flat(json.loads(raw))[k]]
```

`flat()` 是把嵌套目录摊成 `{点分键: 值}` 的递归函数，**一次 ≈ 1.5 万次字典操作**。
写在推导式的**条件**里，就是**每个键调用两次**：`1.5 万 × 2 × 1.5 万` ≈ 4.5 亿次操作，
而且第二个还要先 `json.loads` 把 1.1 MB 重新解析一遍——**每轮 1.5 万次 JSON 解析**。

`added += 1` 那个循环本身是 O(13)，完全无辜；慢的全在这行「安全网」上。
`--dry` 也慢，因为它照样跑断言。

## 修法

每个方向只摊平一次，存成 map 再比：

```python
was = flat(json.loads(raw))      # 一次
...
now = flat(catalog)              # 一次
changed = [k for k in set(was) & set(now) if now[k] != was[k]]
```

八个语种全跑：**0.46 秒**（原来一个语种都跑不完）。

## 怎么避免

- **推导式的条件里不许出现「整对象重算」的函数**：`flat(...)`、`json.loads(...)`、
  `sorted(...)`、`re.findall` 全文扫——它们在单键用例下看着无害，放大到全目录就是 O(n²)
- 写「自查断言」时先估一次规模：这批目录 1.5 万键，任何 O(n) 函数放进 O(n) 循环都是事故。
  **安全网自己必须是廉价的**，否则它会在你最需要它的时候伪装成「程序卡死」
- 判断是不是复杂度问题而不是死锁：把规模砍到 1 个键跑一遍，秒回就是 O(n²)；
  还是不动才是真挂住。这比加 print 快
- 顺带一条：这类脚本先跑 `--dry` 并把**耗时**打出来。这次我先跑 `--dry` 却仍然挂住，
  才说明「dry 不是廉价路径」——廉价与否要量，不要假设
