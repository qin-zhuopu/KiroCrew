# 08 · 发布应用（按验收状态定形态）— 细节验收文档

对应顶层：`00-顶层端到端验收.md` 步骤 **publish-app**（前序 dev-full-phase，后序 view-history）。

## 颗粒度约定（本文档的断言锚点规则）

- **前台断言只认 `data-testid`**，不认组件名、不认文案、不认 CSS。下列 testid 是契约：前端实现时必须带上，验收测试只按 testid 定位。
- **后台断言认端点**：每个后台事实给出「端点 + 请求/响应关键字段」，断言读 JSON，不读日志措辞。
- **进程级断言**（停旧起新）用 PID/端口/HTTP 探活，属于第三层锚点，只有它无法用前两层表达。

## 〇-1、发布视图的结构（入口断言的承接物）

「点击发布页签后发布视图在右侧边栏展开」不是一句空话——展开的是下面这个固定结构，验收逐块对：

| 区块 | 承载 testid | 数据来源（承接前序） |
|---|---|---|
| 版本选择区 | `ai-studio-publish-version-select` | **承接 02-需求文档修改与提交**：选项=该项目已提交的版本列表，与 DocEditor `version-history-list` 同源数据（版本快照接口），不是另造的版本来源 |
| 形态预览 + 原因 | `ai-studio-publish-form-preview` / `ai-studio-publish-form-reason` | 承接 07 的验收记录（demo/full 通过状态） |
| 发布按钮 | `ai-studio-publish-confirm`（复用 `release-btn` 实例） | 前端按「版本 hash vs 最新发布 hash」对比决定渲染与否（见 §〇） |
| 发布结果条 | `ai-studio-publish-status` / `ai-studio-publish-form-badge` / `ai-studio-publish-url` / `ai-studio-publish-record` | 本步自身产出 |
| 版本状态列表块 | `ai-studio-publish-version-list` / `ai-studio-publish-version-state` | 承接 02 的版本列表（每版本一行）+ 本步的发布记录 |

后序文档（09 view-history）承接本步的产出：发布记录、应用地址——已在其视图内列为可跳转节点。

## 〇、发布入口与域名契约

- **入口在应用上下文内**：用户已打开某项目的工作台（`/ai-studio/projects/<id>`），在**右侧边栏点「发布」页签**进入发布视图，对着**具体某个版本**发版；版本号是前序步骤（提交/开发/验收）产生的，本步不允许手输版本号。项目列表是独立路由 `/ai-studio`，发布操作不发生在列表页。
- **域名模板**：`{版本号}-{应用名}-{工号}.gb10.jereh-pe.cn`
  - 版本号在域名最前段；例：应用 `crm`、版本 `v3`、工号 `14409` → `v3-crm-14409.gb10.jereh-pe.cn`
  - 断言：`ai-studio-publish-url` 的 href 必须逐字匹配该模板；版本号/应用名/工号三段都要与当前上下文一致，不允许出现与所选版本不符的域名。
- **发布按钮按「版本 hash vs 最新发布 hash」对比决定**（Owner 已拍板）：每个版本对应一个 commit hash。对每个版本，将其 hash 与**当前最新一次成功发布的 hash** 对比：相同 → 该版本**不渲染发布按钮**、标「已发布」（不渲染，不是禁用）；不同 → 正常渲染发布按钮（含 hash 发布过但非最新的旧版本——那是一次回滚式重发）。再发与最新 hash 相同的版本不产生新实例、不产生新记录。

## 一、发布前的状态前提（fixture）

| 前提 | 断言方式 |
|---|---|
| 目标项目存在至少一个已提交版本 | 版本列表接口返回该版本 |
| 该版本有验收记录，且记录里演示版/完整版各自带 通过/未通过 状态 | 验收记录端点（见 §三） |
| 当前存在一个"旧实例"在跑（已发布过的应用） | 旧实例探活 URL 返回 200 |

## 二、前台操作与断言（data-testid）

### 场景 A：完整版已过验收 → 发布完整版

| # | 操作 | 定位 | 断言 |
|---|---|---|---|
| A1 | 在右侧边栏点「发布」页签 | `ai-studio-publish-entry`（页签本体，挂在 ToolSidebar 内） | 可见、可点击；点击后发布视图在右侧边栏展开，展开结构=§〇-1 的固定区块表（尤其版本选择区已列出前序提交产生的版本） |
| A2 | 选择版本 | `ai-studio-publish-version-select` | 选项含目标版本号；选项只来自前序产生的版本，无手输框 |
| A3 | 发布前形态预览 | `ai-studio-publish-form-preview` | 文本=「完整版」；依据区 `ai-studio-publish-form-reason` 含「完整版验收通过」 |
| A4 | 点击发布 | `ai-studio-publish-confirm` | 点击后进入发布中状态 |
| A5 | 发布中 | `ai-studio-publish-status` | 文本含「发布中」（轮询刷新，非一次性文案） |
| A6 | 发布成功 | `ai-studio-publish-status` | 文本含「发布成功」 |
| A7 | 形态标识 | `ai-studio-publish-form-badge` | 文本=「完整版」 |
| A8 | 发布地址可点 | `ai-studio-publish-url`（链接） | href 匹配域名模板 `{版本号}-{应用名}-{工号}.gb10.jereh-pe.cn`（见 §四探活） |
| A9 | 发布记录可见 | `ai-studio-publish-record` | 含：版本号、形态、需求版本号、关联 Jira 任务号 |
| A10 | 侧栏发布状态 | `ai-studio-publish-version-list` | 该应用每个版本一行；已发布的行标 `ai-studio-publish-version-state` 文本=「已发布」，未发布的=「未发布」；**侧栏只呈现已发/未发两态，不混入其他状态** |
| A11 | 状态回写 | — | 场景 A 发布成功后回到侧栏，该版本行「未发布」→「已发布」，其余版本行不变 |

### 场景 B：仅演示版过验收 → 只发演示版

在 A 的基础上，A3 预览文本=「演示版」；`ai-studio-publish-form-reason` 含「完整版未通过验收」；A7 徽标文本=「演示版」。其余步骤同 A。

### 场景 C：都没过验收 → 拒绝发布

| # | 操作 | 断言 |
|---|---|---|
| C1 | 选该版本 | `ai-studio-publish-form-preview` 文本=「无法发布」 |
| C2 | — | `ai-studio-publish-form-reason` 含「验收未通过」 |
| C3 | 尝试点发布 | `ai-studio-publish-confirm` 为禁用态（disabled），或点击后 `ai-studio-publish-rejected` 可见且含拒绝原因 |

### 场景 D：版本 hash 与最新发布 hash 相同 → 无发布按钮（幂等）

| # | 操作 | 断言 |
|---|---|---|
| D1 | 选一个版本，其 commit hash 与最新一次成功发布的 hash 相同 | `ai-studio-publish-confirm` **不存在于 DOM**（不是禁用，是不渲染） |
| D2 | — | `ai-studio-publish-form-preview` 文本=「已发布」；`ai-studio-publish-url` 仍可见可点（指向已有发布地址） |
| D3 | — | 侧栏（A10）该版本=「已发布」；重复进入发布视图，不产生第二条发布记录（B3 记录数不变） |
| D4 | 选一个 hash 发布过但**非最新**的旧版本（发新版后回看旧版） | `ai-studio-publish-confirm` 正常渲染（回滚式重发允许）；发布后最新发布 hash 指向旧 hash，原最新版本随之变回「未发布」判定口径（按钮恢复渲染） |

## 三、后台断言（端点）

> 端点路径前缀 `/api/apps/ai-studio`；最终路径以实现为准，实现时若调整必须同步改本文档（同一提交）。

| # | 事实 | 端点 | 断言字段 |
|---|---|---|---|
| B1 | 形态判定 | `GET /publish/preview?project&version` | `form: "full"|"demo"|"rejected"`；`reason` 非空；判定来源=验收记录（`acceptanceRef` 指向具体验收记录 id） |
| B2 | 触发发布 | `POST /publish` body `{project, version, commitHash}` | 响应含 `deploymentId`；`commitHash` 与最新成功发布的 hash 相同 → 不新建部署，返回既有 `deploymentId` 与 `idempotent: true`；hash 非最新（含发布过的旧 hash）→ 正常新建部署（回滚式重发）；同 hash 发布进行中再调返回 409 |
| B3 | 发布记录 | `GET /publish/records?project` | 最新记录含：`form`、`version`、`requirementVersion`（关联冻结的需求版本）、`jiraTaskIds` 非空、`status: "success"`、`url`（url 逐字符合域名模板） |
| B4 | 侧栏两态来源 | `GET /publish/records?project` | 每个版本可由记录推导出 已发布/未发布 两态；侧栏渲染与该数据一致（无记录=未发布） |
| B5 | 旧实例被替换 | 探活（无端点，见 §四） | 发布前记录旧 URL 的进程标识，发布后该实例不复存在 |

**幂等与并发**：B2 返回 409 的场景必须有（发布进行中重复点击）；发布失败（构建失败/端口占用）时 B2 响应 `status:"failed"` 且 `ai-studio-publish-status` 文本含「失败」+原因。

## 四、进程级断言（停旧起新）

1. 发布前：`curl -s -o /dev/null -w '%{http_code}' <旧实例URL>` = 200，记录其 PID（或容器 id）。
2. 发布后：旧 PID 不存在（`kill -0` 报错）或旧端口无监听（`ss -tln` 不含旧端口）。
3. 新实例：`ai-studio-publish-url` 的 href 探活 = 200，且页面能完成一次核心操作（用被发布形态自己的验收断言集跑最小一条，完整版用完整版断言、演示版用演示版断言）。
4. **单实例替换语义**：同一时刻同一项目只有一个实例在服务；不允许新旧并存。

## 六、前端组件枚举与复用（防膨胀）

原则：**先复用现有组件，再新建**；本文档的 testid 挂在组件渲染出的 DOM 元素上——验收只认 testid，组件重构不毁断言，但 testid 不许丢。

### 复用（不新建）

| 组件（`website/src/apps/ai-studio/`） | 现有 testid | 本文如何用 |
|---|---|---|
| `ReleaseControl.tsx` | `release-btn` / `distill-btn` / `dev-btn` | **发布确认按钮复用它**，即 §二的 `ai-studio-publish-confirm` = `release-btn` 所在实例（版本上下文中那份）；不另造发布按钮 |
