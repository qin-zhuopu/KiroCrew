# AI Studio——顶层端到端验收（v0.2，按 Owner 口径重写）

> 目的：验证业务用户能否在我们的 AI Studio 上完成一轮"需求驱动开发"闭环：**改需求 → 提交出奇数版 → 图谱反向生成偶数版 → 需求冻结 → 增量任务拆解同步 Jira → 评审 → dev-dag 调度并行/串行开发 → 部署应用 → 全程可追溯 → 下一轮**。
>
> 原则：怎么使用，就怎么验收。本文件是顶层结构，只写主路径与整体通过标准；每步的可执行细节（DOM data-testid 操作 + 逐条断言）拆到细节文档 01~N。
>
> 步骤不使用序号，只使用唯一名字（括号内 slug）。每步标注前序/后序步骤形成双向链表，插入新步骤只改相邻两步的链接，不触发全文改号。
>
> 与参考文档（../AI Coding平台文件/）的口径差异不藏，逐处标 [差异]。

## 核心机制（验收前必读）

- **奇偶版本规则**：需求文档的提交产生**奇数版本**（v1、v3、v5…，来源=人工/AI 修改）；需求图谱经脚本**反向生成**需求文档产生**偶数版本**（v2、v4、v6…，来源=结构化数据重生成）。任何时刻能从版本号奇偶判断文档的来源性质。
- **需求冻结**（替代参考文档中不准确的"发版"）：把某版需求图谱标记为不可变基线，作为本轮任务拆解与开发的唯一依据；重复冻结同一版本被拒绝。
- **增量拆解**：任务拆解 agent 对比新版需求图谱与冻结基线的**增量**，再与**现有代码**对比，得出"哪些要新建任务、哪些已完成任务要重新打开"，直接同步 Jira。
- **Jira 即任务台账**：任务的阻塞/被阻塞关系构成 DAG；对 Jira 的全部操作封装为 **MCP 工具**（Agent 通道，无状态；CLI/jc jira 为人类通道），Agent 只调用不自研同步；dev-dag agent 按 DAG 调度，并行任务各起独立 dev agent + 独立 worktree，**串行任务复用同一个 worktree 目录**（避免目录爆炸）。
- **开发分两阶段**：先开发**演示版**（纯前端，可交互演示全部业务流程），用户确认没问题后再开发**完整版**（含后端）。演示版和完整版都必须通过端到端验收测试才算各自完成。
- **发布按验收状态定形态**：用户可选择发布某项目的某个版本。该版本的**完整版已通过验收→发布完整版**；**只有演示版通过验收→只发布演示版**；两者都没过验收→不可发布。发布形态由验收记录自动判定，不由用户口头声明。
- **星型通信与 master**：架构为星型——**需求 agent 是 master（中心）**：唯一与用户对话的入口，掌握需求文档、奇偶版本、冻结基线的全部上下文；任务拆解 agent、dev-dag agent 是它派出的 spokes，结果回汇、由它向用户汇报。master 不亲自调度 dev：把"对开发"整块委托给 dev-dag agent，只收其结果，防止过程细节撑爆中心上下文。
- **Agent 立法**：全链路固定新增三类 Agent——**需求 agent**（陪聊写需求文档、按图谱 schema 把非结构化文档拆解为结构化图谱数据入库）、**任务拆解 agent**（图谱增量 vs 现有代码→新建/重开任务）、**dev-dag agent**（调度，外加按并行度伸缩的 dev agent）；验收与发布默认用脚本，能脚本的绝不立 Agent。
- **发布是终点**：一轮迭代的收口是应用被真实发布、可访问（参考 hello-app 链路：构建→停旧起新→域名可访问）。

## AC-E2E-001 完成一轮需求驱动开发闭环

### 初始条件

- 已存在一个 AI Studio 项目，含当前需求文档（奇数版）、对应需求图谱、一个已冻结的旧基线。
- 项目已有关联代码库与历史 Jira 任务（部分已完成）。
- 用户具备修改需求、冻结、评审任务、发起开发的权限。

### 验收步骤

#### 步骤：打开当前项目（open-project）
- **执行者分工：** 用户=打开工作台、确认项目与版本；代码=加载需求基线/图谱快照/Jira 任务/部署记录并渲染；Agent=无
- **前序步骤：** （无，入口步骤）
- **后序步骤：** edit-requirement
- **从哪里开始：** 用户刚进入 AI Studio，准备开始下一轮需求迭代。
- **用户做什么：** 打开项目工作台。
- **去了哪里：** 进入项目工作台。
- **用户看到什么：** 当前项目、当前需求文档版本（含奇偶标记）、需求图谱入口、上一轮部署的应用地址、进行中的任务。
- **页面有什么变化：** 项目内容与版本信息加载完成。
- **后台发生什么：** 加载需求基线、图谱快照、Jira 任务列表与部署记录。
- **怎样算通过：** 用户能确认进入正确项目，看清当前版本与上一轮成果。

#### 步骤：修改需求文档（edit-requirement）
- **执行者分工：** 用户=在对话区提需求、修改内容、保存；**Agent=需求 agent（陪聊澄清需求、按需求文档模板组织成文）**；代码=保存修改、记录 Diff 与来源
- **前序步骤：** open-project
- **后序步骤：** commit-odd
- **从哪里开始：** 用户正在查看当前需求文档。
- **用户做什么：** 直接修改一处业务需求并保存（本期所有修改来源记为人工；AI 对话修改为后续扩展）。
- **去了哪里：** 仍停留在需求文档。
- **用户看到什么：** 修改后的内容与本次修改的差异记录。
- **页面有什么变化：** 内容更新，出现 Diff。
- **后台发生什么：** 保存修改，记录 Diff 与来源。
- **怎样算通过：** 修改生效且差异可查。

#### 步骤：提交 → 生成奇数版本与需求图谱（commit-odd）
- **执行者分工：** 用户=点提交、填说明、确认；**Agent=需求 agent（从非结构化需求文档拆解出结构化知识图谱数据——按图谱 schema 抽取实体/属性/关系——并保存到图谱数据库）**；代码=生成奇数版本快照、调图谱入库接口、建立文档↔图谱版本级关联（req2kg 脚本作为反向生成与一致性校验工具保留）
- **前序步骤：** edit-requirement
- **后序步骤：** regen-even
- **从哪里开始：** 用户检查完差异，确认提交。
- **用户做什么：** 点击"提交"，填写说明并确认。
- **去了哪里：** 留在项目，可查看新提交记录。
- **用户看到什么：** 提交成功；产生**奇数版本**（如 v3），出现提交记录与版本标识。
- **页面有什么变化：** 未提交修改变为已提交，版本列表新增奇数版本。
- **后台发生什么：** 生成奇数版本快照；由该版本文档生成/更新**需求图谱**，文档与图谱建立版本级关联。
- **怎样算通过：** 奇数版本存在、图谱已随该版本更新、两者可互相追溯。

#### 步骤：图谱反向生成偶数版本文档（regen-even）
- **执行者分工：** 用户=打开反向生成结果、对比成组 Diff；代码=脚本（req2kg render）从图谱反向生成文档、存偶数版本；Agent=无
- **前序步骤：** commit-odd
- **后序步骤：** freeze-requirement
- **从哪里开始：** 提交已完成，图谱已更新。
- **用户做什么：** 打开反向生成结果（或系统自动生成后提示查看）。
- **去了哪里：** 进入反向生成的文档视图。
- **用户看到什么：** 一份由最新图谱生成的**偶数版本**文档（如 v4），可与奇数版对比。
- **页面有什么变化：** 版本列表新增偶数版本，带"图谱反向生成"来源标记。
- **后台发生什么：** 脚本按固定模板从图谱重生成文档，保存版本及来源关系。
- **怎样算通过：** 偶数版本存在且确来自图谱；与奇数版的 Diff 能让用户判断系统理解是否符合意图（成组 Diff：奇→图谱→偶）。
- **[差异] 演示桩说明：** 机制已在 team-pack 用 req2kg 脚本真验证（parse/render/compare 闭环 + 反例 counter-proof），应用内接通是本验收要覆盖的。

#### 步骤：需求冻结（freeze-requirement）
- **执行者分工：** 用户=点需求冻结、确认版本；代码=标记冻结基线、生成冻结记录、重复冻结硬拒（409）；Agent=无
- **前序步骤：** regen-even
- **后序步骤：** increment-breakdown
- **从哪里开始：** 用户核对完奇偶版本一致，准备锁定本轮需求基线。
- **用户做什么：** 点击"需求冻结"，确认版本号。
- **去了哪里：** 进入冻结后的基线信息。
- **用户看到什么：** 基线版本号、冻结说明、不可变标识。
- **页面有什么变化：** 该图谱版本出现"已冻结"标识与冻结记录；再次冻结按钮变为不可用。
- **后台发生什么：** 图谱版本标记为冻结基线，生成冻结记录；对同一版本的重复冻结请求被硬拒（409）。
- **怎样算通过：** 基线已锁定可引用，重复冻结被拒绝且有明确提示。

#### 步骤：增量任务拆解（increment-breakdown）
- **执行者分工：** 用户=点拆解任务、审阅推理链；**Agent=任务拆解 agent（分析图谱增量、对比现有代码、产出新建/重开候选）**；代码=呈现分析过程与结果
- **前序步骤：** freeze-requirement
- **后序步骤：** sync-jira
- **从哪里开始：** 基线已冻结，进入任务拆解。
- **用户做什么：** 点击"拆解任务"。
- **去了哪里：** 进入拆解过程/结果视图。
- **用户看到什么：** 拆解 agent 的分析过程与结果：新版图谱相对冻结基线的**增量设计事实**清单。
- **页面有什么变化：** 出现拆解任务及其状态，逐步展示候选变化。
- **后台发生什么：** 任务拆解 agent 分析图谱增量，与现有代码对比，产出任务候选：新建任务描述 + 需重开的已完成任务清单。
- **怎样算通过：** 能看到"图谱改了什么→代码缺什么→因此需要哪些任务"的完整推理链。

#### 步骤：同步 Jira（新建 + 重新打开）（sync-jira）
- **执行者分工：** 用户=确认同步；代码=执行同步（新建任务/重开已完成任务附评论/建立阻塞关联），对 Agent 以 **MCP 工具**形式提供（挂 kirocrew-core MCP server，无状态，遵循 docs/architecture/mcp.md 的"模型用 MCP 孪生、CLI 留给人"规则）；jc jira 继续作为人类运维通道，两者不必同实现；Agent=任务拆解 agent 仅以工具调用方式触发同步，不承担同步逻辑
- **前序步骤：** increment-breakdown
- **后序步骤：** review-tasks
- **从哪里开始：** 拆解结果已确认。
- **用户做什么：** 点击"同步到 Jira"（或确认拆解结果自动同步）。
- **去了哪里：** 进入任务列表视图。
- **用户看到什么：** **新增的 Jira 任务**（带描述与验收标准）和**重新打开的已完成任务**（带重开原因）。
- **页面有什么变化：** 任务列表更新，新任务标"新增"，重开任务标"重新打开+原因"。
- **后台发生什么：** Jira 中新建任务、将已完成任务流转回待办并附重开评论；任务间阻塞/被阻塞关联按拆解结果建立。
- **怎样算通过：** Jira 与应用内列表一致：该新建的新建、该重开的重开，且 DAG 关系可见。

#### 步骤：评审任务（review-tasks）
- **执行者分工：** 用户=逐个评审（改/砍/通过）；代码=评审结论写回 Jira（状态/标签）、被砍任务流转取消；Agent=无
- **前序步骤：** sync-jira
- **后序步骤：** dev-demo-phase
- **从哪里开始：** 任务已同步，用户想把关后再开发。
- **用户做什么：** 逐个查看新增/重开任务，调整（改描述/改优先级/砍掉不做的）后确认评审通过。
- **去了哪里：** 仍在任务列表。
- **用户看到什么：** 每个任务有"待评审/通过/砍掉"状态；通过的任务形成可执行的待办集。
- **页面有什么变化：** 评审状态更新，"开始开发"按钮随通过数激活。
- **后台发生什么：** 评审结果写回 Jira（标签/状态），被砍任务流转取消并记录原因。
- **怎样算通过：** 评审结论真实落到 Jira，未被评审的任务不能进入开发。

#### 步骤：开始开发——阶段一：演示版（dev-dag 调度）（dev-demo-phase）
- **执行者分工：** 用户=点开始开发；**Agent=dev-dag agent（读 Jira DAG、派任务、管 worktree 隔离/复用）+ N 个 dev agent（领任务写码）**；代码=渲染 DAG 与状态、记录调度日志
- **前序步骤：** review-tasks
- **后序步骤：** demo-acceptance
- **从哪里开始：** 评审通过，用户准备开发。
- **用户做什么：** 点击"开始开发"（先出演示版）。
- **去了哪里：** 进入开发执行视图。
- **用户看到什么：** 任务 DAG 图（阻塞/被阻塞关系可视化），各节点状态：排队/进行中/完成；进行中的任务显示所属 dev agent 与 worktree；本轮阶段标记为"演示版（纯前端）"。
- **页面有什么变化：** dev-dag agent 启动，DAG 上节点状态开始流转。
- **后台发生什么：** dev-dag agent 领取无阻塞的任务派给 dev agent；**并行任务各自独立 worktree，串行后继任务复用前驱的 worktree 目录**；演示版范围的产物为纯前端可交互应用。
- **怎样算通过：** DAG 调度真实发生：并行任务同时进行且 worktree 互不冲突，串行任务在前继完成后于同一 worktree 继续，全程有调度日志。

#### 步骤：演示版端到端验收与用户确认（demo-acceptance）
- **执行者分工：** 用户=查看验收结果、试用演示版、决定继续或回退（回边→edit-requirement）；代码=执行端到端验收测试套件（细节文档 01~09 断言集）、固化结果与"已通过验收"状态；Agent=无（如用验收 agent 则替代测试脚本执行，二选一）
- **前序步骤：** dev-demo-phase
- **后序步骤：** dev-full-phase、edit-requirement（回边：用户不满意，改需求重走）
- **从哪里开始：** 演示版开发完成（DAG 全绿）。
- **用户做什么：** 对演示版执行端到端验收测试；全部通过后试用演示版，确认"没问题，继续开发完整版"（或提出修改，沿回边回到 edit-requirement）。
- **去了哪里：** 进入演示版验收与试用视图。
- **用户看到什么：** 端到端验收测试的逐条结果（通过/失败），以及可操作的演示版应用。
- **页面有什么变化：** 验收全绿后演示版标记"验收通过"，出现"继续开发完整版"入口。
- **后台发生什么：** 端到端验收测试（01~09 细节文档的断言集）对演示版产物执行并固化结果；结果关联需求版本。
- **怎样算通过：** 验收测试结果真实可查，演示版获得"已通过验收"状态——这是后面发布形态判定的依据。

#### 步骤：阶段二：完整版开发与验收（dev-full-phase）
- **执行者分工：** 用户=点开发完整版、验收后确认；**Agent=dev-dag agent + dev agent（同 dev-demo-phase 规则）**；代码=执行完整版端到端验收并固化结果
- **前序步骤：** demo-acceptance
- **后序步骤：** publish-app
- **从哪里开始：** 演示版已通过验收且用户确认继续。
- **用户做什么：** 点击"开发完整版"；完成后对完整版执行端到端验收。
- **去了哪里：** 进入完整版开发执行视图。
- **用户看到什么：** 后端任务的 DAG 流转（复用同一套调度与 worktree 规则），完成后是完整版验收结果。
- **页面有什么变化：** 新一轮 DAG 流转；验收全绿后完整版标记"验收通过"。
- **后台发生什么：** 后端任务经 dev-dag 调度开发，产物含后端；端到端验收对完整版执行并固化结果。
- **怎样算通过：** 完整版通过同一套端到端验收，获得"已通过验收"状态。

#### 步骤：发布应用（按验收状态定形态）（publish-app）
- **执行者分工：** 用户=选项目与版本、点发布、打开发布地址验证；代码=查验收记录自动定形态（完整版/演示版/拒绝）、构建、停旧实例起新实例、注册访问、关联发布记录；Agent=无（如用发布 agent 则替代构建脚本，二选一）
- **前序步骤：** dev-full-phase
- **后序步骤：** view-history
- **从哪里开始：** 开发完成，用户准备发布。
- **用户做什么：** 选择项目与版本，点击"发布"。
- **去了哪里：** 进入发布视图。
- **用户看到什么：** 系统判定的发布形态及依据：该版本完整版已通过验收→发布完整版；只有演示版通过→发布演示版（附提示"完整版未通过验收"）；都没过→发布被拒。
- **页面有什么变化：** 部署状态从进行中变为成功，出现可点击的应用地址与形态标识（完整版/演示版）。
- **后台发生什么：** 系统查验收记录自动定形态；构建产物、**停旧实例、起新实例**（单实例替换），注册访问入口；发布记录关联应用版本、形态、Jira 任务、需求版本。
- **怎样算通过：** 用户打开发布地址能实际操作对应形态的应用；形态判定与验收记录一致；旧实例已被替换；发布记录可追溯到本轮需求版本。
- **[差异] 当前最大缺口：** ai-studio 应用内未接通真实发布；hello-app/team-pack 侧已验证停旧起新链路。此步是产品化补齐的核心。

#### 步骤：查看全程历史（view-history）
- **执行者分工：** 用户=打开历史、点节点展开与跳转；代码=加载对应状态快照渲染全链路（跳转=快照，不做反向计算）；Agent=无
- **前序步骤：** publish-app
- **后序步骤：** next-round
- **从哪里开始：** 应用已部署上线。
- **用户做什么：** 打开项目历史。
- **去了哪里：** 进入全程历史时间线。
- **用户看到什么：** 需求修改→提交→奇偶版本→冻结→拆解→Jira 同步→评审→开发→部署的完整链路，节点可展开、可跳回对应视图。
- **页面有什么变化：** 历史按时间与关联串联。
- **后台发生什么：** 读取并关联全链路记录；跳转=加载对应状态快照。
- **怎样算通过：** 从部署结果能向前追溯到需求最初修改，中间无断链、无伪造记录。

#### 步骤：继续下一轮（next-round）
- **执行者分工：** 用户=点继续设计；代码=切换新草稿态、保留上一轮全部历史；Agent=无
- **前序步骤：** view-history
- **后序步骤：** 
- **从哪里开始：** 本轮已上线，用户要开始下一轮需求。
- **用户做什么：** 点击"继续设计"。
- **去了哪里：** 回到需求文档编辑器。
- **用户看到什么：** 当前线上需求（偶数版）为新起点，上一轮全部历史可查。
- **页面有什么变化：** 进入未修改状态，历史保留。
- **后台发生什么：** 以上一轮部署对应的需求基线为新起点。
- **怎样算通过：** 可直接开始下一轮，上一轮结果不丢失，闭环成立。

### 总体验收标准

- [ ] 一名业务用户不需要理解图谱、状态机、SDD 或代码，即可走完主路径。
- [ ] 需求修改、提交、反向生成、冻结、拆解、开发、发布是**七类不同且可追溯的事实**。
- [ ] 开发两阶段各以端到端验收收口：演示版未过验收不能进完整版，验收结果被固化并作为发布依据。
- [ ] 发布形态由验收记录自动判定：完整版过→发完整版；仅演示版过→只发演示版并明示；都没过→拒绝发布。
- [ ] 版本奇偶规则全链路成立：任何版本可一眼判断来源（人工提交=奇，图谱反生=偶）。
- [ ] 文档↔图谱双向不造假：正向生成图谱、反向生成文档都有真实对应物，反向有反例验证非平凡。
- [ ] Jira 是唯一任务台账：新建/重开/评审结论/DAG 关系在 Jira 与应用内始终一致。
- [ ] dev-dag 调度正确：并行任务 worktree 隔离、串行任务 worktree 复用、无遗漏无死锁。
- [ ] 每轮收口是真实部署：应用可访问、旧实例被替换、记录可追溯。
- [ ] 从任一最终结果可追溯全链路，且可从部署结果开启下一轮，闭环可持续。
